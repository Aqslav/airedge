# AirEdge — edge-платформа моніторингу якості повітря

**Автор:** Антон Мудрий · курс МПП · індивідуальний проєкт

AirEdge — це програма, яка працює **на краю мережі** (edge, наприклад Raspberry Pi біля датчиків) і:

1. опитує датчики якості повітря (PM2.5, PM10, CO₂, температура, вологість);
2. **валідує** дані, відкидає сміття від збійних датчиків;
3. зберігає їх **локально** в SQLite (нормалізована схема, транзакції);
4. рахує **AQI** (US EPA) і формує **сповіщення** з гістерезисом;
5. надсилає дані в «хмару» за схемою **store-and-forward** — якщо зв'язку немає, дані копляться
   й доставляються пізніше, без втрат і дублікатів (експоненційний backoff);
6. віддає дані через **REST API** та простий **веб-дашборд**.

Фізичних датчиків немає, тому використовується **муляж** (`SimulatedSensor`): випадкове блукання
з поверненням до середнього + імітація збоїв (датчик мовчить, NaN/мінусові значення, епізоди
забруднення). Реальний датчик підключається реалізацією того самого інтерфейсу `Sensor.read()`.

## Архітектура

```
 SimulatedSensor ─┐
 SimulatedSensor ─┼─► [черга, обмежена] ─► валідація ─► SQLite ─► AlertEngine ─► alerts
 SimulatedSensor ─┘      (backpressure)        │          │
                                                │          └─► outbox ─► sync (backoff) ─► «хмара» (файл JSONL)
                                                └─► відхилено (лічильник)
                                       SQLite ─► REST API (/latest, /readings, …) + дашборд "/"
```

| Модуль | Призначення |
|---|---|
| `airedge/sensors/` | інтерфейс `Sensor`, муляж `SimulatedSensor`, `FaultProfile` |
| `airedge/validation.py` | перевірка ім'я/метрики/діапазону/часу |
| `airedge/storage.py` | SQLite: схема, транзакції, параметризовані запити, outbox |
| `airedge/aqi.py` | розрахунок AQI для PM2.5/PM10 |
| `airedge/alerts.py` | пороги warning/critical + гістерезис |
| `airedge/pipeline.py` | черга → валідація → збереження → сповіщення, лічильники |
| `airedge/uplink.py` | відправка в хмару, backoff, `sync_once` |
| `airedge/runtime.py` | `EdgeNode`: потоки датчиків/обробки/синхронізації, коректна зупинка |
| `airedge/api.py` | REST API + дашборд (стандартна бібліотека) |
| `airedge/cli.py` | команди `run` і `report` |

## Вимоги

* Python **3.10+** (перевірено на 3.10 і 3.12)
* для **запуску** зовнішні бібліотеки **не потрібні** (лише стандартна бібліотека)
* для тестів і лінтера: `pip install -r requirements-dev.txt`
* ОС: Linux, Windows, macOS (CI перевіряє всі три)

## Швидкий старт (з нуля)

```bash
git clone <URL-репозиторію> airedge
cd airedge

# 1) запуск на 30 секунд із 3 муляжами датчиків; відкрийте http://127.0.0.1:8080/
python -m airedge run --duration 30 --seed 1
```

(у Windows замість `python` можна `py`). Під час роботи в консолі видно збої датчиків,
відхилені показання та сповіщення. Після завершення друкується підсумок.

```bash
# 2) звіт із бази
python -m airedge report

# 3) приклад API (поки вузол працює)
curl http://127.0.0.1:8080/latest
curl "http://127.0.0.1:8080/readings?device=sensor-01&metric=pm25&limit=5"
curl "http://127.0.0.1:8080/aggregate?device=sensor-01&metric=pm25&bucket=60"
curl http://127.0.0.1:8080/alerts
curl http://127.0.0.1:8080/stats
```

### Сценарії для демонстрації

```bash
# «погана хмара»: 70% відправок падають → дані буферизуються, потім доганяються
python -m airedge run --duration 30 --uplink-failure-rate 0.7

# «забруднення»: часті епізоди → з'являються сповіщення warning/critical
python -m airedge run --duration 30 --episode-rate 0.2 --seed 3

# швидка перевірка: БД у пам'яті, без API
python -m airedge run --duration 5 --db :memory: --port -1
```

### Параметри `run`

| Параметр | За замовч. | Опис |
|---|---|---|
| `--db` | `airedge.db` | файл SQLite (`:memory:` — у пам'яті) |
| `--sensors` | 3 | кількість датчиків-муляжів (1–100) |
| `--interval` | 1.0 | період опитування, с |
| `--duration` | 30 | тривалість, с (`0` — до Ctrl+C) |
| `--seed` | — | seed для відтворюваних даних |
| `--fault-rate` | 0.05 | ймовірність збою датчика |
| `--episode-rate` | 0.02 | ймовірність епізоду забруднення |
| `--cloud-file` | `cloud_sink.jsonl` | файл-імітація хмари |
| `--uplink-failure-rate` | 0.2 | ймовірність обриву зв'язку |
| `--sync-interval` | 2.0 | період синхронізації, с |
| `--port` | 8080 | порт API (`0` — вільний, `-1` — вимкнути) |
| `--log-file` | — | додатково писати журнал у файл |

## REST API (лише читання)

| Маршрут | Параметри | Відповідь |
|---|---|---|
| `GET /` | — | веб-дашборд |
| `GET /health` | — | `{"status":"ok"}` |
| `GET /devices` | — | список пристроїв |
| `GET /latest` | `device` (необов.) | останні значення + AQI на пристрій |
| `GET /readings` | `device`, `metric` (обов.), `since`, `until`, `limit` | історія |
| `GET /aggregate` | `device`, `metric` (обов.), `bucket` (с), `since`, `until` | avg/min/max/count по вікнах |
| `GET /alerts` | `limit` | останні сповіщення |
| `GET /stats` | — | лічильники вузла та БД |

Некоректні параметри → `400` із поясненням; невідомий маршрут → `404`.

## Обмеження (свідомі межі обсягу)

* «Хмара» — це файл JSONL; доставка **at-least-once** (при аварії між відправкою й позначкою пакет піде повторно,
  дедуплікація на боці хмари за `(device, metric, ts)`).
* API лише для читання, без автентифікації; за замовчуванням слухає `127.0.0.1`.
* AQI рахується для PM2.5 та PM10 (US EPA); інші метрики мають лише пороги сповіщень.
* Один процес; для сотень датчиків знадобиться asyncio або кілька процесів.
