## B1. Ланцюг issue → branch → PR → коміти → review → merge

Шаблони вже є: `.github/ISSUE_TEMPLATE/task.md` і `.github/pull_request_template.md`.
Список задач з назвами гілок — у `docs/ISSUES.md`.

**Порядок роботи для кожної задачі:**

1. Створити issue (шаблон «Задача», з дедлайном і Definition of Done).
2. `git switch -c feature/<номер>-<коротко>` від `main`.
3. Коміти у форматі `тип(область): що зроблено (#N)`, напр. `feat(storage): outbox для store-and-forward (#4)`.
4. Pull Request з `Closes #N`; дочекатися зеленого CI.
5. Рев'ю (див. B3), виправлення за коментарями.
6. Merge у `main` (squash або merge-commit), гілку видалити.

**Для захисту підготуйте 2–3 приклади повного ланцюга** (посилання на issue → PR → коміти → рев'ю → merge),
що охоплюють: код, архітектурне рішення (запис у `LOGBOOK.md`), тести, документацію, debugging.

> ⚠️ Історію git не можна «намалювати» заднім числом: викладач оцінює реальний ланцюг і авторство «за виконаною
> роботою». Тому почніть робити issues/PR зараз і переносіть код у репозиторій по задачах (див. `docs/ISSUES.md`).

## B3. Результативність code-review

Зараховуються лише **результативні** рев'ю: ви перевірили **чужий** PR → знайшли суттєву проблему або запропонували
обґрунтоване покращення → автор відреагував → ви перевірили виправлення. ≥3 → 1.0; 2 → 0.8; 1 → 0.5.

Оскільки команди немає, рев'ю «в себе» не рахуються. Реальні варіанти:

1. **Взаємне рев'ю з одногрупником:** ви рев'юєте його PR-и, він — ваші (у вашому репозиторії PR-и від нього можуть бути
   маленькими: README, тест, виправлення).
2. Узгодити з викладачем, чиї PR вам рев'ювати.
3. Рев'ю в open-source-проєкті (дрібні PR із суттєвим зауваженням).

| Учасник | Рев'ю (посилання на PR) | Суттєва проблема / пропозиція | Реакція автора | Перевірено |
|---|---|---|---|---|
| Антон Мудрий | | | | |

Чекліст суттєвого рев'ю: коректність на крайніх випадках, потокобезпека, безпека (ін'єкції, валідація), відсутні тести,
порушення архітектури, регресії. **Дрібні косметичні коментарі не рахуються.**

## D1. Складність і повнота зони відповідальності

Зона: **весь проєкт** (одноосібно). Що реалізовано і чим це складно:

| Область | Що зроблено | Складність |
|---|---|---|
| Конкурентність | потік на кожен датчик + споживач + синхронізатор; обмежена черга з backpressure; коректна зупинка (порядок join, дочитування черги, flush) | висока |
| Надійна доставка | store-and-forward: транзакційний outbox, експоненційний backoff, catch-up пакетами, ідемпотентність за `UNIQUE` | висока |
| Дані | нормалізована схема SQLite, обмеження цілісності, часткові індекси, агрегація в SQL, ретеншн (`purge_sent`) | середня/висока |
| Предметна логіка | AQI за методикою US EPA (усікання, інтерполяція по брейкпоінтах); автомат сповіщень із гістерезисом | середня |
| Імітація реальності | муляж: випадкове блукання з поверненням до середнього, епізоди забруднення, збої (мовчання, NaN, викиди) | середня |
| Інтерфейси | REST API (валідація, 400/404), веб-дашборд, CLI | середня |
| Якість | 173 тести, 99% покриття, pylint 10/10, CI на 3 ОС | — |

Самооцінка: **просунута, повністю й якісно виконана** зона (рівень 0.9 за шкалою D1; «експертна» — розподілені воркери — не заявляється).

**Короткий захист (≈2 хв):** «Edge-вузол збирає дані з датчиків, перевіряє їх, зберігає локально й надійно доставляє в хмару навіть
при втраті зв'язку. Найскладніше — узгодити потоки та гарантувати, що дані не губляться й не дублюються. Ось демо…» →
запустити сценарій «погана хмара» з README.
